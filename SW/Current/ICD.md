# MiniLoRa ICD — Interface Control Document (v3)

**Version:** 3.6 · **Date:** 2026-11-04 · **FW:** ≥ 2.6.0 · **Status:** canonical

> **3.6 (FW 2.6.14): sleep duration over LoRaWAN (SET_RANGE)** — new fPort-3
> command **SET_RANGE (`0x07`)**: `arg` = the **index into kSleepTableMs**
> (0–8: 1, 2, 5, 10, 15, 20, 30, 60, 120 min) — the same scale the config
> envelope's `cfgRange` and the app's config tab use. Saved to NVS; out-of-
> range indices are ignored. Takes effect at the end of the cycle it is
> processed in; the **confirm rides the next telemetry frame's
> sleep-minutes byte (fPort-1 byte 26)** — no diag change. This restores
> the v1 sleep downlink (removed in 3.1) in the modern frame format.
>
> **3.5 (FW 2.6.11): remote config over LoRaWAN + diagnostics schema 0x05** —
> new fPort-3 command **CFG_SET (`0x06`)**: `arg` bit7 = value, bits 0–3 =
> flag id (1 WiFi, 2 Zigbee, 3 BLE beacon, 4 GNSS, 5 BME280, 6 OPT3001,
> 7 LIS3DH) — see §3. **LoRaWAN itself is deliberately not addressable** (it
> is the lifeline). The state confirm rides the new diag byte 28
> **configFlags** (schema **0x05**, 29 bytes): the runtime transport/sensor
> enables as `kCfgFlag*` bits — bit0 WiFi … bit6 LIS3DH — mirrored from the
> config on every diag. BLE *config* paths (long-press, recovery, remote BLE
> window) are ungated on `cfgBLE`; only the telemetry beacon follows the
> flag. Decoders accept 0x03 (24 B), 0x04 (28 B) and 0x05 (29 B); on
> pre-0x05 frames the config state is simply unknown (null).
>
> **3.4 (FW 2.6.6): fPort-1 byte 20 (`sats`) re-defined** — it now carries the
> **satellite count tracked during the window** (last GGA), populated even when
> no fix was accepted (0 = window skipped or the module was silent). Fix
> validity remains keyed on the **position bytes** (`gps_valid` = lat/lon ≠ 0,
> decoder-derived) — never on `sats > 0`. Same 28-byte layout, same byte
> positions; firmware no-fix path, TTN decoder comment, Android app and this
> document updated in lockstep. Golden vectors unaffected (encode/decode of
> byte 20 unchanged). Rows are self-describing: `sats > 0 && lat == 0` simply
> means "the module saw satellites but never fixed".
>
> **3.3 (FW 2.6.1): payload pressure scale re-defined** — fPort-1 bytes 2–3
> now carry pressure in **0.1 hPa units** (deci-hPa) instead of integer hPa:
> range 0–6553.5 hPa at 0.1 hPa resolution (600–1100 hPa with 10× the old
> precision). Same 28-byte layout, same byte positions; only the scale of
> one field changed. All consumers (firmware, TTN decoder, Android app,
> MiniLoRa-server, golden vectors) updated in lockstep; golden vectors
> regenerated. Rows stored before 2026-11-02 read 10× low.
>
> **3.2 (FW 2.6.0): diagnostics schema 0x04** — 28 bytes, adds lastTtff /
> linkMargin / gwCnt / otaStatus (bytes 24–27). Decoders accept 0x03 (24 B)
> and 0x04.

> **3.1 (FW 2.4.0): v1 compatibility removed.** The 158/159-byte legacy
> config writes, the legacy config-read echo and the v1 fPort-1 downlink ABI
> (sleepIdx/gpio6) are gone — see §3 and §4.

This is the **single source of truth** for every wire interface of the
MiniLoRa tracker. Other documents (`payload_format.md`,
`BLE_CHARACTERISTIC.md`, `GOLDEN_VECTORS.md`) are historical or consumer-side
views and link here.

Golden vectors for **all** frames below are generated by
`Firmware/tools/gen_vectors.py` into `host_tests/vectors/`
(`payload_v1.json`, `icd_v3.json`). **The generator is the contract.**

## 1. Telemetry uplink — fPort 1, 28 bytes 🔒 FROZEN

See `Android-MiniLoRa/payload_format.md` and `GOLDEN_VECTORS.md`. **Do not
change a byte** — three consumers (v1 firmware, TTN decoder, Android) already
speak it. No-fix GPS cycles send a **zero position**; consumers detect that
with `lat == 0 && lon == 0` (decoder-derived `gps_valid`; the diag frame
carries the explicit `gpsValid` bit, see §2). Since **3.4**, byte 20 (`sats`)
carries the tracked-satellite count whenever the GNSS window ran — even
without a fix — and must **not** be used as a fix signal.

## 2. Diagnostics uplink — fPort 2, 24 bytes (schema 0x03) / 28 bytes (schema 0x04) / 29 bytes (schema 0x05)

Sent every `kDiagSendEveryCycles` (16) boots, or on the `SEND_DIAG` command.
Sent **after** the telemetry uplink of the same cycle, so counter increments
of that cycle are included. `gpsValid` refers to that cycle's telemetry.
A **LinkCheck is requested on every diag uplink**; the answer (margin +
gateway count) describes that uplink and is reported in the *next* diag
frame (RTC-persistent), 255 = unknown.

**WiFi parallel** (FW 2.6.1): when WiFi is configured and a diag frame is
due, the device also POSTs the identical frame to
`http://IP:PORT/diag?device=NAME` in its WiFi phase — the only diag source
when LoRaWAN is down or disabled (and a fresher snapshot when both run:
it includes the WiFi-phase counter increments). The server dedups
retries for 60 s on `(device_id, raw_hex)`.

| Byte | Field | Type | Notes |
|---|---|---|---|
| 0 | **schema** | `0x03` | decoders switch on this byte, forever |
| 1–3 | fw version | 3 × u8 | major, minor, patch |
| 4–5 | bootCount | u16 LE | increments every boot |
| 6–7 | unexpectedResets | u16 LE | boot-loop guard counter |
| 8 | lastResetReason | u8 | `esp_reset_reason_t` value |
| 9–10 | gpsTimeouts | u16 LE | saturating |
| 11–12 | loraJoinFailures | u16 LE | saturating |
| 13–14 | loraSendFailures | u16 LE | saturating |
| 15–16 | wifiFailures | u16 LE | saturating |
| 17–18 | zigbeeFailures | u16 LE | saturating |
| 19–20 | sensorReadFailures | u16 LE | saturating |
| 21 | gpsConsecFails | u8 | indoor-backoff counter (cleared on fix) |
| 22 | powerFlags | u8 | bit0 = degraded (<3500 mV), bit1 = critical (<3300 mV) |
| 23 | flags2 | u8 | bit0 = gpsValid (this cycle), bit1 = OTA pending-verify, bit2 = recovery mode |
| 24 | lastTtff | u8 | last successful GPS TTFF, seconds; 255 = unknown *(v4)* |
| 25 | linkMargin | u8 | LinkCheck margin dB from the previous diag uplink; 255 = unknown *(v4)* |
| 26 | gwCnt | u8 | gateways that heard it (same provenance); 255 = unknown *(v4)* |
| 27 | otaStatus | u8 | 0 none, 1 staged, 2 no-server, 3 download-failed, 4 bad-image *(v4)* |
| 28 | configFlags | u8 | runtime transport/sensor enables (see §3 CFG_SET): bit0 WiFi, bit1 Zigbee, bit2 BLE beacon, bit3 GNSS, bit4 BME280, bit5 OPT3001, bit6 LIS3DH *(v5)* |

All multi-byte fields little-endian. Unknown schema → ignore frame, log.
Schema 0x03 frames (FW ≤ 2.5.x) end at byte 23; schema 0x04 (FW ≤ 2.6.10)
end at byte 27 — decoders accept all three.

## 2.1 Position history uplink — fPort 4 (store-and-forward, FW ≥ 2.6.0)

Emitted on GPS-less cycles (every `kSendEvery`=4th, when history exists):
the **two most recent fixes** so a tracker that lost sight of the sky still
reports where it was, and when.

```
0      schema  = 0x01
1      count   = 1..2
2..    entries, OLDEST first, 13 bytes each:
         0-3   latitude  int32 LE microdegrees
         4-7   longitude int32 LE microdegrees
         8-11  time      uint32 LE unix epoch of the fix (0 = unknown)
         12    sats      uint8
```

The buffer holds the last 8 fixes in NVS (`hist` namespace) and survives
power cycles. The server stores each entry as a reading with source
`wifi`/`ttn`/`ttn-hist` provenance.

## 3. Downlink — fPort 3 commands (3 bytes)

Frame: `[0x4D][opcode][arg]`. Applied at the start of the **next** cycle
(RTC flags survive deep sleep). Unknown opcodes ignored (forward-compatible).
**No secrets are ever accepted over downlink** — key material only via BLE.

*Removed in ICD 3.1 (FW 2.4.0):* the v1 fPort-1 downlink ABI (byte0 =
sleepIdx, byte1 = gpio6Control). Sleep duration is now changed exclusively
via the config envelope; a fPort-1 downlink is simply ignored.

| Opcode | Name | arg | Effect |
|---|---|---|---|
| `0x01` | LOCATE_NOW | — | force GPS window next cycle (overrides indoor backoff & low-battery skip; never critical battery) + sleep 60 s after it |
| `0x02` | SEND_DIAG | — | diag uplink (fPort 2) next cycle |
| `0x03` | RESET_DIAG | — | clear all failure counters + boot-loop guard (bootCount kept) |
| `0x04` | BLE_WINDOW | — | 120 s BLE config service next cycle |
| `0x05` | OTA_UPDATE | — | pull firmware from the MiniLoRa-server next cycle (see §9); honored even in degraded battery, never in critical. **(3.6) if WiFi is disabled, it is temporarily forced on for the pull and restored to the previous state once the OTA flag is consumed** |
| `0x06` | CFG_SET | bit7 = value, bits0–3 = flag id | set a transport/sensor enable next cycle; persisted to NVS; a diag is armed so the confirm rides the next frame *(3.5)* |
| `0x07` | SET_RANGE | sleep-table index (0–8) | set the wake-cycle interval next cycle-end; persisted to NVS; the confirm rides the next fPort-1 frame's sleep-minutes byte *(3.6)* |

**CFG_SET flag ids** (arg = `(value << 7) | id`, e.g. `0x06 0x81` = WiFi ON,
`0x06 0x84` = GNSS OFF). The state is mirrored in diag byte 28
(`configFlags`, bit `1 << (id-1)`):

| id | Flag | Notes |
|---|---|---|
| 1 | WiFi | telemetry push + OTA |
| 2 | Zigbee | telemetry stack |
| 3 | BLE beacon | the **telemetry beacon only** — BLE config (long-press, recovery, remote window) is always available |
| 4 | GNSS | GPS windows |
| 5 | BME280 | env sensing |
| 6 | OPT3001 | lux sensing |
| 7 | LIS3DH | accelerometer |

**LoRaWAN is deliberately not addressable** — it is the lifeline; no flag id
maps to it. Unknown flag ids are ignored (forward-compatible).

**SET_RANGE** uses the sleep-table index, not minutes (the table is firmware
fixed: 1, 2, 5, 10, 15, 20, 30, 60, 120 min). Indices ≥ 9 are ignored.

**§1 accelerometer bytes (7–9) unit clarification (3.6):** the ±10000 map
carries **LIS3DH 10-bit counts at the configured ±4 g full scale**, not
milli-g — 1 g of gravity = 512 counts, so a device flat on a table reads
Z ≈ 128 + 6.5 = 134 on the byte (≈ 0.43 on the old mis-scaled /1000
display). Consumers convert to mg at ×4000/2048 (≈ ×1.953); the server and
the Android app do this as of FW 2.6.14's decode.

| 0x08–0xFF | — | reserved | ignored (forward-compatible) |

## 4. BLE config — characteristic `0000CAFE-…`

Write-with-response. **Since ICD 3.1 (FW 2.4.0) only CRC envelopes are
accepted** — legacy raw blobs are rejected
(`BLE_ATT_ERR_INVALID_ATTR_VALUE_LEN`) and the config is left untouched.
A corrupted write can therefore never misconfigure keys.

| Schema | Total length | Body | Notes |
|---|---|---|---|
| 3 | 163 B | 159 B (v1 layout + cfgZigbee) | still accepted; asset fields default |
| 4 | 168 B | 164 B = 159 + 5 asset bytes | still accepted; P2P fields default |
| **5** | **193 B** | **189 B** = 164 + 25 P2P bytes | **current — see §10** |

**v3 envelope (163 bytes):**

| Byte | Field |
|---|---|
| 0 | magic `'C'` (`0x43`) |
| 1 | schema version = 3 |
| 2–160 | `DeviceConfig` body, 159 B — the v1 158-byte layout + `cfgZigbee` (see `BLE_CHARACTERISTIC.md` for field table) |
| 161–162 | CRC16-CCITT (poly `0x1021`, init `0xFFFF`) over bytes 2–160, little-endian |

Bad magic/version/CRC → `BLE_ATT_ERR_INVALID_ATTR_VALUE_LEN`, config
**unchanged**. A corrupted write can no longer misconfigure keys.

**IP field wire order** (subtle): `wifiServerIP` octets are stored in
*octet order* — `192.168.1.10` → bytes `C0 A8 02 28` at offset 96. The
Android app packs the u32 MSB-first (`0xC0A80228`) and stores it
BIG_ENDIAN; both produce the same bytes. Do not "fix" either side to LE.

**Read** returns the schema-4 envelope of the **current** config (magic,
schema 4, 164-byte body, CRC) — the app verifies the CRC of what it read
back. (Before ICD 3.1 this read echoed the raw 158-byte legacy blob.)

**Asset-mode body bytes (schema 4, offsets 159–163):** `cfgAssetMode`
(bool, wake on LIS3DH motion), `cfgMotionSens` (1 = 128 mg, 2 = 256 mg,
3 = 512 mg), `cfgAssetHeartbeatH` (0 = 24), `cfgBurstIntervalMin`
(0 = 5), `cfgBurstMaxPerDay` (0 = 20). In asset mode the tracker sleeps
until motion (INT1 → EXT1) or the heartbeat timer; motion wakes force a
GPS window (capped per day via net time) and re-report at the burst
interval. NVS schema 3 stores the full 164-byte struct; schema 2 blobs
(159 B) zero-fill the asset tail.

**P2P body bytes (schema 5, offsets 164–188):** `cfgLoRaMode` (u8,
0 = LoRaWAN — default, 1 = P2P star), `cfgP2PRole` (u8, 0 = leaf,
1 = gateway), `cfgP2PProfile` (u8, 0 = long-range SF12 — default,
1 = balanced SF10, 2 = bench SF7), `cfgP2PRxAfterTx` (u8, 0 off,
1 on — default), `cfgP2PShortId` (u32 BE, 0 = derive from the last
4 bytes of the DevEUI), `cfgMeshKey` (16 B — the shared mesh PSK;
**all-zero keeps P2P disabled** regardless of `cfgLoRaMode`, so a key
must be provisioned before the radio talks), `cfgP2PTxPower` (u8,
0 = default 14 dBm; 14–22 dBm honored, legal to 27 dBm ERP on the
869.4–869.65 sub-band — see §10.2). NVS schema 5 stores the full
189-byte struct; schema 3/4 blobs zero-fill the P2P tail. The firmware
writes schema 5 and accepts 3, 4 and 5 on write.

## 6. BLE beacon

Extended-advertising coded PHY, 625 ms interval; manufacturer-data body is
the 28-byte payload v1 frame verbatim (after a 2-byte company id).

## 7. Versioning rules

1. **fPort 1 (28 B) is frozen.** New telemetry fields never go there; they
   ride the diag frame or a new fPort.
2. **Every variable frame starts with a schema byte.** Bump it on any change;
   keep decoding old schemas where practical.
3. **BLE config**: a new layout means a new envelope version byte (4, 5, …).
   Since 3.1 the firmware accepts exactly one format (the current envelope);
   older blobs are rejected outright.
4. **Golden vectors are the contract**: change `gen_vectors.py` first, then
   make firmware/decoder/app agree with it.

## 9. OTA pull (HTTP, device → MiniLoRa-server)

The device never accepts pushed images — it **pulls** from the server it
already has configured (`wifiServerIP:port`, the WiFi-transport endpoint):

```
GET /ota/check?device=<DevEUI hex>&current=<fw version>
  -> 200 {"update": true, "version": "…", "size": N,
          "sha256": "<64 hex>", "path": "/ota/download/<id>"}
  -> 200 {"update": false}      (or 404 — treated the same)
GET /ota/download/<id>          -> streamed .bin, exactly `size` bytes
```

Rules: the image is written to the **passive slot** and SHA-256-verified
**before** the boot partition is switched; any mismatch/abort leaves the
running image untouched (rollback protection still applies on top). Plain
HTTP is acceptable on a LAN because the digest authenticates the image —
enable the check only on networks you control. The download happens inside
one wake cycle (~2 MB ≈ seconds); a failed download simply retries on a
later trigger.

## 8. WiFi telemetry push (HTTP, device → MiniLoRa-server)

When `cfgWiFi` is set, the device POSTs the 28-byte payload v1 frame
verbatim (`application/octet-stream`) to its configured endpoint once per
cycle, then parks the radio:

```
POST http://<wifiServerIP>:<port>/data?device=<globalName>
```

* The `?device=` query parameter carries the configured device name — the
  server must key readings by it, **never by the client IP** (DHCP
  re-addressing would otherwise orphan the history). A push without the
  parameter falls back to the client IP (v1 server compatibility).
* The request body is exactly the fPort-1 frame; no wrapping, no token
  (bench/LAN deployments; `push_token` exists server-side if needed).

## 10. P2P star transport — raw SX1262, no infrastructure (FW ≥ 3.0.0)

**Decision log:** 2026-11-09 — cloud-free operation requested; merged as
config (`cfgLoRaMode`), not a fork. Star topology (one gateway + leaves)
chosen over mesh: no TTL, no relay budget, no routes. Leaves are
**TX-only** to preserve the µA sleep budgets; the gateway listens and is
powered. GPS+RTC time sync on every node enables a slotted air schedule
instead of random access. Air profile: SF12 @ 869.525 MHz (10 % duty
sub-band) default. Mesh PSK from the config envelope. OTA stays
WiFi/USB-only — the mesh never carries firmware.
2026-11-09b — **boot counter in the header + CTR IV** (security review):
a seq reset on battery swap would have reused recorded keystreams
(two-time-pad); the NVS-backed power-cycle counter rides the frame and
the IV, making the keystream unique per boot with zero coordination.

### 10.1 Roles

| Role | Config | Radio | Power model |
|---|---|---|---|
| **Leaf** | `cfgLoRaMode=1, cfgP2PRole=0` | TX own frames + short RX-after-TX window; never listens otherwise | unchanged µA budgets |
| **Gateway** | `cfgLoRaMode=1, cfgP2PRole=1` | listens on the slot grid, forwards heard frames + its own over WiFi, delivers commands | deep-sleeps between windows (~1 mA target) |

A device is either LoRaWAN or P2P — the SX1262 has one air interface.
Roles are per-device config; a leaf is promoted to gateway by a config
write, never a reflash.

### 10.2 Air profile

| Profile | Freq | SF | BW | Notes |
|---|---|---|---|---|
| 0 long-range (default) | 869.525 MHz | 12 | 125 kHz | DE on; ~2.1 s per telemetry frame |
| 1 balanced | 869.525 MHz | 10 | 125 kHz | ~4× shorter frames, ≈ half the range |
| 2 bench | 869.525 MHz | 7 | 125 kHz | fast benching only |

TX power defaults to 14 dBm and is configurable to **22 dBm**
(`cfgP2PTxPower`) — the sub-band allows 27 dBm ERP, so +22 dBm with a
2 dBi antenna (~24 dBm EIRP) stays legal. Every dB is ≈ 20 % more range;
+8 dB ≈ 2.5×. The SX1262 pulls ~170 mA at 22 dBm — fine for the powered
gateway, budget it for solar leaves.

Sync word **private** (`0x12/0x34`) — P2P and LoRaWAN traffic cannot see
each other. CR 4/5, preamble 8, explicit header, CRC handled by the
frame (§10.3), radio CRC off. All nodes in a mesh MUST share the
profile; the gateway can report a profile mismatch as silence.

### 10.3 Frame format (on-air, 20+n bytes)

```
0      1      2                 6          10        11      13    14    14+n  18     20
+------+------+-----------------+----------+---------+-------+-----+------+-----+------+
| ver  | type | origin_id (u32) | seq (u32)| hops(1) |boot(2)| len | body | mic | crc16|
| 0x01 |      | BE, short id    | BE       | 0       | BE    |  n  |      | 4 B | 2 B  |
```

* `type`: 0x01 telemetry (body = §1 payload v1, 28 B), 0x02 diagnostics
  (§2 body), 0x03 history (§2.1 body), 0x04 command (§3 3-byte body,
  `0x4D op arg` verbatim), 0x05 slot assignment (v2).
* `origin_id`: the **sender's** short id — §4 `cfgP2PShortId`, default
  the last 4 bytes of the DevEUI (BE). It is the server `device_id`.
* `seq`: per-origin counter, +1 per frame, persisted across sleeps
  (RTC). It is the delivery-ratio counter — the server stores it in the
  `f_cnt` column so §7 analytics apply unchanged. A power cycle resets
  it; the **boot** counter below makes that harmless.
* `boot`: the sender's power-cycle counter (u16, wraps at 65,536) — it
  rides the CTR **IV** (`origin || seq || boot || 6×0x00`), so a battery
  swap can never reuse a recorded keystream (the recorded-frames XOR
  attack). Stateless: receivers read it from the header, no lookup. NVS
  write per power cycle only.
* `hops`: always 0 in the star (reserved for later multi-hop).
* `crc16`: CCITT poly `0x1021` init `0xFFFF`, over bytes 0…14+n+4
  (everything before the CRC), little-endian — the ICD-wide convention.
* `mic`: first 4 bytes of AES-CMAC(`cfgMeshKey`, bytes 0…14+n) — the
  body is AES-CTR-encrypted with the same key (IV above). A frame
  failing CRC **or** MIC is dropped silently.

### 10.4 The slot grid (GPS-anchored, 60 s superframe)

Time comes from the GPS/RTC pair every node already keeps (sub-second).
The grid is **absolute**: `superframe = floor(gps_epoch / 60)`,
`slot = floor((gps_epoch % 60) / slot_len)`.

| Region | Slots (at SF12) | Use |
|---|---|---|
| Data | 16 × 3 s | scheduled telemetry, history, diag |
| Catch | 2 × 3 s | emergencies, off-schedule wakes, new-leaf announce |
| Reserve | 2 × 3 s | gateway command TX, overflow |

`slot_len = ceil(airtime(profile) × 1.5)`; the slot count per superframe
is `60 / slot_len` — SF10 yields 1-s slots (60 of them: 52 data, 4
catch, 4 reserve). The split is 80/10/10 of the slots, minimum 2 catch.

* **Leaf TX slot** = `hash(origin_id, superframe) % n_data` (FNV-1a).
  Collisions move between superframes instead of repeating; the leaf
  CADs ~50 ms before TX — busy → skip to the next superframe's slot.
* **Leaf scheduling**: the leaf computes its next slot ≥ `sleep_min`
  away and sets the **RTC alarm** to that exact second (wake 500 ms
  early for sensor reads). No waiting while awake.
* **Catch slots**: any off-schedule wake (asset motion, LOCATE_NOW,
  button, first boot) TXes in the next catch slot (≤ 60 s wait). The
  gateway **always** wakes for catch slots — this is how new leaves
  announce themselves (`origin`, `sleep_min` in the body) and how
  emergencies are never missed.
* **Command window**: a leaf opens a 2 s RX window right after its own
  TX (`cfgP2PRxAfterTx`) — the gateway answers a heard frame with a
  queued command frame addressed to that leaf, same slot region. ~11 µA
  per day at a 30-min cycle.
* **Gateway cycle**: deep-sleep; wake for (a) catch slots every 60 s
  (2 × 3 s RX), (b) predicted leaf slots — learned from received
  frames (`origin`, `sleep_min`, phase), (c) its own hash slot to TX
  its own telemetry, (d) a flush+push window when the forward queue is
  non-empty. Dedup cache `(origin, seq)` lives in LP RAM and survives
  sleep.

### 10.5 Gateway → server forwarding

```
POST /p2p?device=<gateway-short-id-hex>[&token=]
Content-Type: application/x-ndjson
{"origin":"AABBCCDD","seq":4271,"ts":1793892967,"hex":"<body hex, §1/§2/§2.1/§3>","rssi":-97,"snr":9.5}
…
```

One NDJSON line per heard frame; the gateway flushes every 10 frames or
60 s, whichever first. The server decodes `hex` with the §1/§2/§2.1/§3
decoders, stores `device_id = origin`, `source = "p2p"`,
`frame_ts = ts`, `f_cnt = seq`, and dedups on `(device, frame_ts,
raw_hex)` exactly like the TTN poller. RSSI/SNR are stored for the link
margin view. The gateway's **own** frames flow through the same batch
(`origin` = itself) — its data path is identical to a leaf's.

### 10.6 What the mesh must never do

* No firmware over the air (§9 stays WiFi/USB).
* No LoRaWAN frames on the P2P profile or vice versa (sync words differ).
* No P2P at all with an all-zero `cfgMeshKey`.

### 10.7 Duty-cycle and power budget (profile 0, 30-min leaves)

| Node | Airtime/day | Avg current |
|---|---|---|
| Leaf TX | 96 × 2.1 s ≈ 3.4 % of the 10 % band | ~71 µA (TX) |
| Leaf RX window | 2 s/cycle | ~11 µA |
| Gateway | catch slots (6 s/60 s) + predicted windows | ~0.8-1.2 mA |

Gateway flash cost sits inside the enlarged OTA slots (partitions
revised 2026-11-09: 1,920 KB per slot, +64 KB each).

### 10.8 Trek mode — two-device bilateral beacon (`cfgLoRaMode = 2`)

Two paired devices (the mesh PSK **is** the pairing — any frame that
authenticates with my key is my peer), each with a phone in BLE range.
Goal: a mutual "still in touch" beacon with **both** positions on both
phones. No gateway, no server; each phone may still push both tracks to
the LAN server when one appears.

**Schedule.** The exchange period is the sleep table (`cfgRange` — both
devices set the same value). Windows anchor to the GPS epoch:
`window ≡ 0 (mod period)`. Each window has three sub-slots of the §10.4
slot length (3 s at SF12):

| Sub-slot | Sender | Listener |
|---|---|---|
| S0 | **lower** short id | higher id |
| S1 | higher short id | lower id |
| S2 | whoever missed their RX re-TXes own frame | the other listens |

* `boot` counter, PSK, profile and `cfgP2PTxPower` are shared config —
  the role is derived from the short ids, nothing else is provisioned.
* **Bootstrap**: before the first contact the peer id is unknown — the
  device assumes the lower-id role (TX S0, RX S1) and **alternates the
  assumption** on each failed window, so first contact lands within ≤ 2
  windows. After the first valid frame the peer id is known and the
  id-order roles are permanent (RTC).
* **Adaptive power** is per-device, driven by its own RX quality: a
  missed exchange or a peer frame at RSSI < −115 dBm steps the level
  **up** the ladder 14 → 17 → 20 → 22 dBm; three consecutive frames at
  RSSI > −110 dBm step it back down one notch (floor 14). The level
  persists in RTC RAM and resets to 14 on power cycle.
* **Contact lost**: 3 consecutive windows without a valid peer frame →
  the green LED plays a 3× double-blink pattern at each wake (visible
  with the phone packed away). Any valid frame clears it.

### 10.9 Peer-relay BLE advertisement (trek + future gateway use)

After an exchange each device advertises **two** extended-adv sets for
`kBeaconDurationMs`: its own §6 beacon (sid 0, unchanged) and a
**peer-relay** set (sid 1) with the peer's last received frame:

```
manufacturer data: FF FF FF | 0x02 | origin (4 B BE) | seq (4 B BE) | body (28 B, §1 plaintext)
```

The leading `0x02` type byte distinguishes it from a plain v1 beacon
(28-byte manufacturer body). The app tags the body under
`deviceKey = origin-hex` and derives contact status from the adv's
freshness — no new GATT, no connection.

### 10.10 What trek mode must never do

* No server dependency: the exchange completes device-to-device.
* No role config: roles derive from the short ids after first contact.
* No LoRaWAN frames on the trek profile (same private sync word as §10).
