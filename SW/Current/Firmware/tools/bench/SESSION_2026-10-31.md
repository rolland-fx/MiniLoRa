## Findings (chronological)

1. **FW version string was stale** — all v2.2–2.6 builds reported `2.1.0`
   because `sdkconfig` pins `CONFIG_MINILORA_FW_VERSION` once generated;
   Kconfig-default bumps never propagated. Fixed (`sdkconfig` now 2.6.0).
   Documented in FLASHING.md.
2. **Partial flash = unbootable** — flashing only the app to 0x20000 over a
   v1 partition table → "No bootable app partitions". Must flash
   bootloader (0x0) + partition table (0x8000) + app (0x20000) — or use
   `idf.py flash`. Documented.
3. **v2.6.0 boots and runs** — banner, cycle start, no panic, full cycle
   completed into deep sleep (port vanished on schedule).
4. **Green LED lit during deep sleep** (user observation) — GPIO6 slept LOW
   while v1 slept HIGH; production green LED is active-low → lit all night,
   ~1–5 mA against a ~30 µA budget. **Fixed** in commit `5f9d724`
   (sleep-time GPIO6 HIGH, v1 parity). **✅ VERIFIED on hardware
   2026-10-31: after flashing the fix, the green LED is dark in deep
   sleep (user confirmation).** D4 charger LED may stay on — different
   LED, netlist-confirmed on the CN3165 CHRG pin.
5. **Charging path verified by observation** — with USB connected the
   charge LED was on (CN3165 actively charging the 1100 mAh cell).
6. **Reset-loop root cause FOUND: ModemManager.** The earlier
   "PWRGLITCH" claim was a misdiagnosis (see below: reason 11 is
   `ESP_RST_USB`, =14 is `PWR_GLITCH`). Kernel evidence: ttyACM0
   re-enumerated every ~61 s for an hour+ (device number climbed past
   104), accelerating to reset-on-boot — **with no capture script
   connected**. ModemManager (running, enabled since Oct 24) probes new
   ACM ports by toggling DTR/RTS + AT commands; on the ESP32-C6
   USB-Serial-JTAG a DTR toggle is a chip reset → probe → reset →
   re-enumerate → probe. Its journal shows it grabbing ttyACM0 before
   (Jul 24/26/27 "port ttyACM0 released"). brltty inactive — ruled out.
   **Fix (user, sudo):**
   ```
   sudo systemctl stop ModemManager
   sudo tee /etc/udev/rules.d/99-espressif-jtag.rules <<'EOF'
   # Espressif ESP32 USB-Serial-JTAG: keep ModemManager away
   SUBSYSTEM=="tty", ATTRS{idVendor}=="303a", ENV{ID_MM_DEVICE_IGNORE}="1"
   EOF
   sudo udevadm control --reload-rules && sudo udevadm trigger
   ```
   Likely also explains the v1-era "WDT issue" (spurious resets while
   USB-connected, blamed on the watchdog) — same phenomenon, different
   suspect. WDT itself is fully ruled out: v1 shipped with no-op
   `feedWatchdog()`; v2 has `ESP_TASK_WDT_PANIC` unset (can print, never
   reset), INT WDT would print a dump (none seen), and a WDT reset would
   latch reason 5/6/7, never 11.
7. **Indoor GPS behaviour confirmed working as designed**: v1 burned its
   full GPS window with no fix; v2.6.0 honours the warm/cold budgets and
   the indoor backoff (exact counters not yet captured — see "pending").

## Final resolution (Nov 1, ~11:30) — ALL GREEN

Bench validation of the fully-fixed firmware (7+ cycles captured clean):
- Sleep/wake: `reset=DEEPSLEEP wake=4` on every boot, zero spurious resets
- GPS window: ran at backoff-scheduled boot 40, warm budget honored,
  indoor timeout correct, consecFails bookkeeping 5→6 exact
- Battery: 4083→4227 mV climbing while charging, readings stable ±3 mV
  after the RC-settling fix — cell + charge path HEALTHY; the morning
  3.56 V was the biased reading (unsettled RC) of a discharged cell
- 5-min bench sleep cap works exactly (remove before field release!)
- Root causes closed: ModemManager probes, our own tooling's DTR
  toggling (4 resets/s cascade captured), GPS probe-before-wake,
  battery ADC under-settling, WDT starvation in BLE windows,
  unvalidated NVS config load. Hardware exonerated throughout.
